# FPS 벤치마크

Raspberry Pi 5 + Adafruit 1.3" TFT Bonnet에서 격투게임 한 장면(배경, 캐릭터 2명, 체력 바, 타이머)을 매 프레임 그리며 최적화 단계별 화면 FPS를 측정한다. 동시에 60Hz 판정 로직 스레드를 돌려, 화면이 느려져도 판정 틱이 일정하게 유지되는지 함께 기록한다.

## 실행

본넷을 연결하고 venv를 켠 상태에서 실행한다.

```bash
python3 fps_bench.py                        # 전체 단계, 단계당 5초
python3 fps_bench.py --secs 15              # 단계당 15초
python3 fps_bench.py --only dirty --cap 60  # 부분 갱신 + 화면 60FPS 상한 (WBS 1.6 확인용)
```

결과는 스크립트 옆에 `results.json`, `results.csv`, `frame_*.png` 로 저장된다.

## 측정 단계

| 단계 | 방식 |
|---|---|
| pil | Pillow로 합성한 뒤 기본 `disp.image()` 로 전송 (SPI 24/40/64/80MHz) |
| numpy | numpy로 RGB565 바이트를 만들어 직접 전송 |
| dirty | 바뀐 영역(상단·하단 HUD 띠, 캐릭터 영역)만 전송 |
| thread | 전송 전용 스레드에 최신 프레임만 넘겨 전송 |

## 결과 (2026-11-17, 1회차, 단계당 5초)

원본 : [`results/results_2026-11-17.csv`](results/results_2026-11-17.csv)

| 단계 | 화면 FPS | 1프레임 전송 | 판정 로직 | 틱 지연 p99 |
|---|---|---|---|---|
| 기준선 : Pillow + `disp.image()`, SPI 24MHz | 19.4 | 50.7ms | 60.0Hz | 1.06ms |
| SPI 40MHz | 29.1 | 33.6ms | 60.0Hz | 2.6ms |
| SPI 64MHz | 39.9 | 24.4ms | 60.2Hz | 2.48ms |
| SPI 80MHz | 39.9 | 24.4ms | 60.2Hz | 2.32ms |
| numpy로 RGB565 직접 전송 | 45.6 | 21.2ms | 60.1Hz | 0.26ms |
| 부분 갱신 (Dirty Rectangle) | 121.8 | 7.6ms | 60.1Hz | 0.2ms |
| 전송 스레드 분리 | 38.8 | 25.8ms | 60.0Hz | 0.3ms |

같은 조건의 2회차(단계당 15초)도 19.2 / 29.5 / 40.5 / 40.5 / 45.6 / 121.8 / 38.2 FPS로 재현되었다.

- 64MHz와 80MHz의 결과가 같아, 클럭만으로는 약 40FPS가 한계다.
- 부분 갱신에서 기준선 대비 약 6.3배가 나왔지만, 121.8FPS에서는 티어링이 보였다. 본넷에 TE 핀이 없어 패널 주사율(약 60Hz)보다 빠르게 쓰면 화면이 찢어지므로, 본 게임에서는 화면을 60FPS로 제한한다.
- 전송 스레드 분리는 합성이 0.6ms밖에 걸리지 않아 겹칠 작업이 거의 없고, 오히려 느려졌다.

> 측정 당시 코드는 부분 갱신 단계에서 하단 HUD를 x 0~160 범위만 다시 보냈다. 지금 코드는 전체 폭으로 고쳤고 `--only`, `--cap` 옵션을 추가했다.
